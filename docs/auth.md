# Авторизация и управление доступом

## Основные архитектурные решения

Система аутентификации приложения строится на Better Auth.

Better Auth интегрируется с Fastify через собственный Fastify-плагин. Конфигурация Better Auth и связанные с ней функции размещаются в отдельном пакете `packages/auth`.

Для хранения данных используется общий пакет `packages/db` на базе Drizzle ORM и PostgreSQL.

Самостоятельный сервис авторизации создавать не требуется.

### Публичный доступ

Агрегатор событий является публичным приложением.

Регистрация и авторизация не обязательны для использования публичного сайта, поиска мероприятий, просмотра карточек событий и взаимодействия с Telegram/MAX-ботами.

Пользователь может подписываться на уведомления в мессенджерах без создания веб-аккаунта.

Публичную регистрацию пользователей сайта в MVP не реализовывать.

### Защищённые функции

Авторизация через Better Auth обязательна для административной панели.

Разграничение доступа осуществляется с использованием ролей и разрешений.

Роли MVP:

* admin;
* editor;
* user.

Роль user предусматривается для возможного дальнейшего развития пользовательских аккаунтов, но публичная регистрация не является частью MVP.

### Модель пользователей

Не создавать отдельную дублирующую таблицу пользователей приложения.

Better Auth управляет своими таблицами пользователей, сессий и способов входа.

Прикладные таблицы ссылаются на пользователя Better Auth по его идентификатору, если такая связь необходима.

Подписчики Telegram/MAX могут существовать без соответствующей учётной записи Better Auth.

### Приоритет требований

Этот документ содержит окончательные требования к авторизации и управлению доступом.

Если первоначальное техническое задание содержит противоречащие положения о регистрации пользователей, самостоятельной реализации сессий или обязательной авторизации для публичного доступа, руководствоваться требованиями настоящего документа.

В процессе проектирования устранить противоречия и привести основное техническое задание в соответствие с этим документом.

# Дополнение к ТЗ: система аутентификации и авторизации

## 1. Выбранная технология

Для проекта необходимо использовать Better Auth в качестве основной системы аутентификации.

Не реализовывать собственный механизм хранения паролей, выдачи сессий и восстановления доступа при наличии соответствующей функциональности Better Auth.

Использовать:

* Better Auth;
* официальный Drizzle Adapter;
* PostgreSQL;
* Better Auth Admin Plugin;
* Better Auth Svelte Client;
* интеграцию Better Auth с Fastify.

Не создавать отдельный HTTP-сервис авторизации в MVP.

## 2. Архитектура

Создать пакет `packages/auth`.

В пакете должны находиться:

* конфигурация Better Auth;
* фабрика создания серверного экземпляра;
* настройки способов входа;
* конфигурация сессий;
* описание ролей и разрешений;
* типизированные функции проверки полномочий.

Better Auth должен использовать общий пакет `packages/db`.

Создать Fastify-плагин, который регистрирует маршруты Better Auth и предоставляет методы проверки сессий и разрешений.

Все запросы к системе аутентификации должны обрабатываться Fastify по пути `/api/auth/*`.

SvelteKit использует Better Auth Svelte Client, но не создаёт второй серверный экземпляр Better Auth.

## 3. Модель данных

Использовать стандартные таблицы Better Auth:

* user;
* session;
* account;
* verification.

Сгенерировать Drizzle-схему с помощью официального CLI Better Auth.

Учитывать таблицы и поля, которые добавляют выбранные плагины.

Все миграции выполнять через Drizzle Kit.

Не создавать дублирующие таблицы пользователей, паролей или сессий.

Прикладные сущности должны ссылаться на `user.id`.

Не изменять служебные таблицы Better Auth без необходимости.

## 4. Способы входа

Для MVP реализовать:

* вход по email и паролю;
* выход из системы;
* получение текущей сессии;
* восстановление пароля;
* завершение пользовательской сессии.

Предусмотреть возможность подтверждения email.

Для отправки писем использовать абстракцию почтового провайдера с тестовой реализацией для локальной разработки.

Публичную регистрацию пользователей можно отключить до реализации личных кабинетов.

Первоначальный администратор должен создаваться безопасным способом через CLI или защищённую процедуру инициализации.

Не использовать общедоступный endpoint для создания первого администратора.

Предусмотреть возможность дальнейшего подключения OAuth и passkeys без изменения модели пользователей.

## 5. Роли и разрешения

Использовать Better Auth Admin Plugin с настраиваемой моделью доступа.

Роли MVP:

* admin;
* editor;
* user.

Разрешения определять для отдельных ресурсов приложения.

Ресурсы:

* events;
* sources;
* venues;
* organizers;
* categories;
* publications;
* users;
* settings.

Предусмотреть отдельные разрешения на создание, редактирование, удаление и публикацию мероприятий.

Редактор не должен иметь возможности управлять администраторами или изменять системные настройки.

Не считать авторизацию на уровне интерфейса достаточной защитой.

Fastify должен проверять сессию и полномочия при выполнении каждой защищённой операции.

## 6. Интеграция с Fastify

Создать Fastify-плагин Better Auth.

Плагин должен:

* регистрировать auth-маршруты;
* корректно передавать запросы и ответы между Fastify и Better Auth;
* сохранять несколько заголовков Set-Cookie при необходимости;
* поддерживать корректную обработку тела запроса;
* учитывать публичный HTTPS-адрес приложения за reverse proxy;
* предоставлять механизм получения текущего пользователя;
* предоставлять защиту маршрутов по ролям и разрешениям.

Не создавать собственный механизм сессий поверх Better Auth.

Не отключать встроенные механизмы безопасности Better Auth для упрощения интеграции.

## 7. Интеграция с SvelteKit

Создать Better Auth Svelte Client.

Реализовать:

* страницу входа;
* страницу восстановления доступа;
* получение текущей сессии;
* защищённые административные маршруты;
* перенаправление неавторизованных пользователей;
* отображение интерфейса в зависимости от разрешений.

Использовать единый публичный origin для сайта и API.

Для серверных запросов SvelteKit к Fastify корректно передавать пользовательские cookies.

Не вызывать проверку сессии из браузера как единственный механизм защиты серверных страниц.

Не создавать дублирующую модель авторизации внутри SvelteKit.

## 8. Безопасность

Настроить:

* HttpOnly cookies;
* Secure cookies для production;
* SameSite;
* CSRF-защиту;
* список доверенных origin;
* ограничение попыток входа;
* безопасное хранение секретов;
* срок действия сессий;
* механизм завершения сессий.

Не хранить токены сессий в localStorage.

Не передавать клиенту секретные поля пользователя.

Не логировать пароли, токены и session cookies.

Проверять актуальность сессии и разрешений при выполнении защищённых операций.

## 9. Telegram и MAX

Не использовать идентификатор Telegram или MAX как прямую замену веб-сессии Better Auth.

Сохранять платформенные идентификаторы в таблице bot_subscriber.

Предусмотреть необязательную связь bot_subscriber.userId с Better Auth user.id.

Пользователь должен иметь возможность пользоваться ботом без веб-регистрации.

В перспективе предусмотреть безопасную привязку аккаунта бота к существующему пользователю сайта.

Для привязки использовать одноразовые токены с ограниченным сроком действия и проверкой владения соответствующей учётной записью.

## 10. Тестирование

Проверить:

* успешный и неуспешный вход;
* создание и завершение сессии;
* истечение срока действия сессии;
* доступ к административным маршрутам;
* разграничение прав admin, editor и user;
* защиту от CSRF;
* работу авторизации при SSR;
* передачу cookies через reverse proxy;
* невозможность получения прав администратора обычным пользователем;
* корректную работу защищённых маршрутов после выхода.

Не считать интеграцию завершённой без тестов реальных HTTP-запросов к Fastify и проверки авторизации в SvelteKit.


# Дополнение к ТЗ: публичный доступ и необязательная авторизация

## 1. Основной принцип

Городской агрегатор событий является публичным сервисом.

Регистрация и авторизация не требуются для просмотра мероприятий, поиска, фильтрации, использования Telegram/MAX-ботов и подписки на уведомления в мессенджерах.

Необходимо обеспечить полноценную работу основного пользовательского функционала без создания учётной записи.

Система авторизации Better Auth используется для доступа к административной панели и, в перспективе, для дополнительных персональных возможностей приложения.

## 2. Публичный сайт

Следующие разделы должны быть доступны без авторизации:

* главная страница;
* каталог мероприятий;
* страницы мероприятий;
* страницы категорий;
* страницы площадок и организаторов;
* поиск и фильтрация;
* переходы на сайты организаторов и сервисы покупки билетов.

Не перенаправлять неавторизованных посетителей на страницу входа.

Не требовать получения пользовательской сессии для выполнения публичных запросов.

Публичные страницы должны корректно работать при отключённых сторонних cookies и отсутствии ранее созданной учётной записи.

## 3. Публичный API

Все GET-запросы к публичному каталогу должны работать без пользовательской сессии.

Примеры:

```text
GET /api/cities
GET /api/events
GET /api/events/:slug
GET /api/categories
GET /api/venues
GET /api/venues/:slug
GET /api/organizers/:id
```

Публичный API должен возвращать только разрешённые к публикации данные.

Не раскрывать внутренние комментарии модераторов, служебные настройки, закрытые данные источников и персональные данные пользователей.

Для публичных запросов предусмотреть разумные ограничения частоты обращений, пагинацию и кеширование, где это необходимо.

## 4. Административная панель

Административная панель обязательно требует авторизации через Better Auth.

Все маршруты `/admin/*` должны проверять действительность сессии пользователя.

Доступ должен предоставляться только пользователям с соответствующими ролями и разрешениями.

Неавторизованный посетитель при попытке открыть административную панель перенаправляется на страницу входа.

При этом серверные административные API должны независимо проверять авторизацию и разрешения.

Недостаточно просто скрыть административные элементы интерфейса.

Обычный пользователь с действительной сессией также не должен получать доступ к административным функциям без соответствующих прав.

## 5. Регистрация пользователей

Для MVP публичная регистрация через сайт не требуется.

Предусмотреть возможность её включения в будущем без переработки архитектуры авторизации.

Первоначального администратора создавать через защищённую процедуру инициализации.

Создание и управление учётными записями редакторов выполняет администратор.

Не создавать пользовательские аккаунты Better Auth автоматически при обычном посещении сайта.

## 6. Telegram и MAX

Использование ботов не требует регистрации на сайте или входа через Better Auth.

При первом взаимодействии с ботом создавать или обновлять запись BotSubscriber на основании проверенного идентификатора пользователя соответствующей платформы.

Пользователь может:

* выбирать город;
* просматривать мероприятия;
* искать события;
* настраивать категории;
* подписываться на уведомления;
* отключать уведомления.

Все эти действия доступны без создания веб-аккаунта.

При необходимости в будущем реализовать необязательную привязку BotSubscriber к учётной записи Better Auth.

Отсутствие такой привязки не должно ограничивать основной функционал бота.

## 7. Необязательная персонализация

Архитектура должна допускать добавление персональных возможностей для зарегистрированных пользователей.

Например:

* синхронизация избранного между устройствами;
* сохранённые поисковые запросы;
* персональные рекомендации;
* единые подписки для сайта, Telegram и MAX.

Эти возможности не входят в обязательный функционал MVP.

Не создавать дополнительную систему пользовательских аккаунтов и не усложнять первоначальную модель данных ради будущей персонализации.

## 8. Критерии готовности

Проверить следующие сценарии:

1. Новый посетитель открывает сайт без регистрации и получает доступ к афише.
2. Неавторизованный посетитель выполняет поиск и открывает карточку мероприятия.
3. Публичный API возвращает опубликованные мероприятия без пользовательской сессии.
4. Посетитель не может получить через публичный API черновики или закрытые данные.
5. Пользователь Telegram/MAX может пользоваться ботом без веб-аккаунта.
6. Пользователь может подписаться на уведомления в мессенджере без Better Auth.
7. Неавторизованный посетитель не может открыть административную панель.
8. Неавторизованный запрос к административному API отклоняется.
9. Авторизованный пользователь без необходимых разрешений не может выполнять административные операции.
10. Администратор с действительной сессией получает доступ к разрешённым административным функциям.

Главное требование: авторизация должна защищать закрытые функции приложения, но не препятствовать использованию публичной городской афиши.
