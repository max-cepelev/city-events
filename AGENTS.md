# City Events — инструкции для AI-агентов

## 1. Назначение проекта

City Events — агрегатор городских мероприятий с публичным сайтом, административной панелью, системой автоматического сбора событий и интеграциями с Telegram и MAX.

Проект разрабатывается как production-ready приложение с возможностью дальнейшего расширения.

## 2. Основная документация

Перед выполнением любых существенных изменений изучи:

* `docs/specification.md` — полное техническое задание;
* `docs/auth.md` — требования к авторизации и управлению доступом;
* `docs/architecture.md` — принятые архитектурные решения, если файл существует;
* `docs/implementation-plan.md` — текущий план и прогресс разработки, если файл существует.

Не полагайся исключительно на контекст предыдущих диалогов.

При обнаружении противоречий в документации сначала установи актуальное решение и приведи документы в соответствие с ним.

Требования `docs/auth.md` имеют приоритет при определении модели авторизации.

## 3. Технологический стек

Использовать:

* TypeScript;
* Node.js;
* SvelteKit;
* Fastify;
* PostgreSQL + PostGIS;
* Drizzle ORM;
* Redis + BullMQ;
* Crawlee;
* Telegram Bot API;
* MAX Bot API;
* pnpm workspaces;
* Turborepo;
* Docker.

Не заменять выбранные технологии без технического обоснования.

## 4. Архитектурные ограничения

Проект реализуется в виде монорепозитория.

Основные приложения:

* `apps/web` — SvelteKit;
* `apps/api` — Fastify;
* `apps/worker` — фоновые задачи и сбор событий;
* `apps/bots` — интеграции с мессенджерами.

Общие пакеты:

* `packages/db`;
* `packages/auth`;
* `packages/core`;
* `packages/queue`;
* `packages/shared`;
* `packages/api-client`;
* `packages/event-sources`;
* `packages/fastify-plugins`.

Fastify является основным backend и предоставляет REST API.

SvelteKit отвечает за публичный сайт, SSR и административный интерфейс.

Drizzle используется в общем пакете БД.

Бизнес-логика должна быть независима от HTTP-фреймворков.

Не создавать отдельный HTTP-сервис для доступа к БД.

Не создавать микросервисы без конкретной технической необходимости.

## 5. Авторизация

Использовать Better Auth в `packages/auth`.

Интегрировать Better Auth с Fastify.

Публичный сайт и пользовательские Telegram/MAX-боты должны работать без обязательной регистрации.

Административная панель требует авторизации и соответствующих разрешений.

Не создавать собственную систему управления паролями и сессиями.

Не дублировать таблицы пользователей Better Auth.

## 6. Работа с существующим кодом

Перед изменением существующего модуля изучи его реализацию и зависимости.

Если в репозитории присутствуют готовые Fastify-плагины, используй их там, где это соответствует архитектуре.

Не переписывай рабочий код без конкретной причины.

При переносе инфраструктурной функциональности в общие пакеты сохраняй совместимость с существующими компонентами, если это возможно.

## 7. Принципы разработки

Придерживайся KISS, DRY и разделения ответственности.

Не добавляй абстракции без реальной потребности.

Не используй `any` для обхода ошибок типизации.

Не создавай фиктивные реализации вместо необходимой функциональности.

Не добавляй новые зависимости без обоснования.

Используй типизированные интерфейсы на границах модулей.

Соблюдай единый стиль кодирования.

Перед использованием сторонних API проверяй актуальную документацию.

## 8. Работа с базой данных

Все изменения схемы выполнять через Drizzle и версионируемые миграции.

Не изменять существующие production-данные без необходимости.

Не выполнять destructive migrations без анализа последствий.

Не создавать соединения с БД при простом импорте пакета.

Каждый процесс самостоятельно управляет своим пулом соединений.

## 9. Фоновые задачи

Использовать BullMQ для очередей и регулярных заданий.

Не выполнять тяжёлые операции внутри HTTP-обработчиков.

Обеспечивать идемпотентность заданий.

Для критически важных событий использовать transactional outbox там, где это предусмотрено архитектурой.

Не использовать локальный EventEmitter для межпроцессного взаимодействия.

## 10. Проверка результатов

После реализации каждого функционального изменения:

1. Проверь TypeScript.
2. Запусти соответствующие тесты.
3. Проверь линтер.
4. Проверь сборку затронутых приложений.
5. Исправь обнаруженные ошибки.
6. Обнови документацию при изменении архитектуры или публичных интерфейсов.

Не сообщай об успешном прохождении проверок, которые фактически не запускались.

## 11. Планирование разработки

Поддерживай актуальность `docs/implementation-plan.md`.

Перед началом следующего этапа проверь состояние уже реализованных компонентов.

Не выполняй масштабные изменения вне текущего этапа без необходимости.

Если обнаружена архитектурная проблема, исправление которой необходимо для дальнейшей разработки, задокументируй принятое решение.

* какие проверки выполнены;
